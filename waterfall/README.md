# 워터폴 기획·개발 템플릿

새 서비스의 문제와 출시 범위를 정의하는 일부터 요구사항, 설계, 검증, 운영 인수까지 프로젝트 결정을 한곳에서 추적하기 위한 Markdown 템플릿입니다.

## 시작하기

1. 첫 기획에서는 [서비스 기획서](00-기획/서비스기획서.md)의 사용자 문제와 근거, MVP 포함·제외 범위, 성공 판단 기준을 작성합니다.
2. 여러 화면이나 역할에서 공유하는 규칙은 [비즈니스 정책서](00-기획/비즈니스정책서.md)에 기록합니다. 승인 전에 확인해야 할 가정과 미결 사항에는 담당자와 결정 기한을 지정합니다.
3. 합의한 범위를 [요구사항 명세서](01-요구사항분석/요구사항명세서-SRS.md)의 검증 가능한 요구사항으로 풀고, [요구사항 추적 매트릭스](01-요구사항분석/요구사항추적매트릭스-RTM.md)에 연결합니다. 여러 역할의 흐름이나 예외가 복잡하면 유스케이스를 함께 작성합니다.
4. 후속 문서는 프로젝트 범위와 위험에 맞게 선택합니다. 문서를 통합하거나 기존 이슈·PR·CI 기록을 쓰면 아래 표에 해당하는 자료의 위치를 검토 기록에 남깁니다.

`[placeholder: …]`나 대괄호로 표시된 입력란을 채우고, 예시 행·수치·기술 스택은 프로젝트 정보로 교체합니다. 확인이 필요한 항목은 `미결`과 담당자·기한을, 적용 범위에 해당하지 않는 항목은 `해당 없음`과 사유를 기록합니다. 예시 승인이나 테스트 결과는 지운 뒤 실제 검토 기록과 증빙을 연결합니다.

## 범위, 검증, 변경 기록

- 범위는 서비스 기획서의 `MVP-001` 또는 `EX-001` 같은 ID로 기록합니다. 포함 항목의 우선순위는 `P1 필수`, `P2 권장`, `P3 선택`을 사용합니다. 우선순위와 별개로 이번 릴리스에 합의한 포함·제외 범위를 명시합니다.
- 정책을 참조할 때는 정책 분류 ID에서 한 단계 내려가 개별 규칙 ID를 사용합니다. 예를 들어 `BP-REQ`가 신청 정책 분류라면 `BP-REQ-001`은 구체적인 규칙입니다.
- 요구사항과 테스트 연결 예시를 한 줄로 읽으면 다음과 같습니다. **`MVP-001` 신청 접수 → `BP-REQ-001` 마감 시각부터 접수 불가 → `FR-001` 신청 제출 → `TC-FN-REQ-001` 마감 직전 허용 / `TC-FN-REQ-002` 마감 시각 거절.** 실제 RTM에는 설계·코드 참조와 테스트 실행 결과도 단계에 따라 연결합니다.
- KPI는 출시 후 사업 가설을 판단하는 지표입니다. 개별 요구사항의 수용 기준에는 테스트에서 판정할 수 있는 조건과 기대 결과를 적습니다.
- 단계 승인 시 대상 문서 버전, 승인자, 날짜, 판단 근거를 [검토 체크리스트](08-검토/단계별검토-체크리스트.md)에 남깁니다. 승인 후 범위나 정책이 바뀌면 [변경 관리 계획](08-검토/프로젝트관리-산출물.md#4-변경-관리-계획)으로 영향을 검토하고 SRS·RTM·관련 검증 항목을 함께 갱신합니다.

[CLAUDE.md](CLAUDE.md)에는 산출물 작성에 참고할 확장 예제가 있습니다. 이 폴더를 복사해 사용할 때는 위 표의 개별 문서에서 시작합니다.
